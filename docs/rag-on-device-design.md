# 端侧 RAG + LLM 检索增强设计

> 主方案：`docs/rust-tauri-refactor-plan.md`。本文补全其 §6（LLM 能力集成）未覆盖的检索层，
> 并把"生成"从「只能调云端」扩展为「端侧优先、云端可选」。
> 已落地的检索内核：`crates/cn-rag`（零第三方依赖，11 个单测全绿）。

---

## 0. 一句话

**索引是派生数据（随时可重建），检索是混合的（中文 bigram BM25 + 稠密向量 + RRF），
路由分三档（结构化走 SQL、语义走 RAG、混合先过滤再检索），生成可切（端侧默认、云端可选）。**

这四句话决定了后面所有取舍：派生索引让迁移零风险，混合检索让中文短查询不依赖分词词典，
三档路由避免"用 RAG 回答我有几个未读"这类必错的聚合问题，可切生成让低端设备也能用。

---

## 1. 硬约束

| 约束 | 取值 | 来源 |
| --- | --- | --- |
| 语料规模 | ≤ 400 条通知、≤ 1000 个块 | `store.mjs` 存储上限 400（传输 200） |
| 端侧 | Windows + Android，离线可用 | 主方案 G1 |
| 体积 | APK ≤ 12 MB、安装包 ≤ 8 MB | 主方案 G6 |
| 隐私 | 默认零出网 | 主方案 S1–S11 |
| 延迟 | 检索 ≤ 200 ms；端到端首 token ≤ 1.5 s（桌面）/ ≤ 3 s（中端手机） | 本文新增 |
| 模型分发 | **不進安装包**，首次使用下载或本地导入 | 体积约束的直接推论 |

最后一条是硬性的：1.1 GB 的量化模型不可能塞进 12 MB 的 APK。所以安装包只带运行时，
模型作为可选资源，缺失时 RAG 整体降级为"纯关键词检索"，功能不中断。

## 2. 三个"不引入"

### 2.1 不引入向量库

1000 块 × 512 维 float32 = 2 MB。暴力余弦是 1000 × 512 ≈ 51 万次乘加：
桌面上约 0.3 ms，中端手机上约 3 ms。HNSW/FAISS 在这个规模上的收益为负——构建耗时、
内存放大、以及一个必须跟着 Rust + Android 一起交叉编译的 C++ 依赖。

**结论：一个 `Vec<i8>` + 线性扫描就够。** 真到了万级再换，接口不变（`retrieve()` 的签名不变）。

### 2.2 不引入中文分词词典

jieba 词典约 3 MB，且"词典里没有这个词"就是硬性漏召回。本场景的查询词集中在
「考试」「奖学金」「四六级」「选课」这类 2–4 字词，**字符 bigram 的召回不低于分词**，
且永远不会因为词典缺词而失效。代价是索引词项变多（每 100 字约 100 个 bigram），
在千级块规模下可以忽略。

`cn-rag::tokenize` 已实现：CJK 连续段取 bigram，西文/数字取小写整词，标点处断开。
单测覆盖 `关于2026年期末考试安排的通知` → 含 `关于` / `2026` / `考试`。

### 2.3 不引入独立数据库

索引放在 `{app_data}/index/` 的派生目录，`store.json` 仍是唯一真值。
好处：删掉索引不影响任何业务数据；从 Node 版迁移时只需重建索引，不需要数据转换；
索引损坏时自动重建而不是让用户看到空列表。

## 3. 索引管线

### 3.1 切块

| 参数 | 取值 | 理由 |
| --- | --- | --- |
| 块上限 | 320 字 | 嵌入模型（bge-small）有效窗口 512 token，中文约 1:1.5 |
| 重叠 | 1 句 | 防止"截止时间在下一句开头"被切断 |
| 单条上限 | 6 块 | 超长公文取前 6 块（含首块标题块），避免一条通知占满上下文 |
| 标题块 | 独立一块，检索得分 × 1.5 | 标题是最强信号，独立成块避免被正文稀释 |

标题还会作为**每个块的前缀**参与嵌入（`cn-rag::embed_input`）：`{标题}\n{块正文}`。
这解决"块脱离上下文"导致的召回偏差——单看"请于 11 月 20 日前提交"不知道是什么事。

### 3.2 嵌入模型选型

| 模型 | 维度 | 体积（int8） | 中文效果 | 许可 |
| --- | --- | --- | --- | --- |
| **bge-small-zh-v1.5**（首选） | 512 | ≈ 24 MB | 同尺寸最强梯队 | MIT |
| multilingual-e5-small | 384 | ≈ 30 MB | 多语言均衡，中文略弱 | MIT |
| text2vec-base-chinese | 768 | ≈ 100 MB | 老牌，体积偏大 | Apache-2.0 |

选 bge-small-zh：512 维让向量存储减半，MTEB 中文检索上与 base 版差距在 1–2 个点，
对 1000 块的语料不构成可感知差异。

### 3.3 存储布局

```
{app_data}/index/
├─ manifest.json    { schema: 1, model: "bge-small-zh-v1.5", dim: 512,
│                     promptVer: 1, chunker: "320/1", count: 1032, builtAt: "..." }
├─ chunks.jsonl     每行 { id, noticeId, ord, text, sourceId, publishedAt, category, deadline }
├─ vectors.bin      连续 int8，长度 = count × dim；末尾附 count × f32 的 scale 表
└─ tombstones.json  已删除的 noticeId（惰性过滤，重建时清空）
```

int8 量化用对称映射（`cn-rag::quantize_i8`），单块 512 B，1000 块约 500 KB。
`manifest.model` 或 `dim` 与当前配置不一致 → 整个目录重建，不做兼容读取。

### 3.4 增量与重建

| 事件 | 动作 |
| --- | --- |
| 新增通知 | 切块 → 嵌入 → 追加；每 20 块批量一次 |
| 通知被移除 | 写 `tombstones.json`；检索后过滤；累计 ≥ 50 条或启动时重建 |
| 设置变更（模型/块参数） | 全量重建 |
| 索引损坏 / 版本不符 | 全量重建，UI 显示进度 |
| 存储被外部编辑 | 启动时比对 `manifest.count` 与 `store.notices.length`，差异 > 20% 重建 |

重建是后台任务，期间检索使用旧索引（读旧 `manifest` 指向的文件），完成后原子切换目录名。

## 4. 检索

### 4.1 双路召回

```
query ──tokenize──▶ BM25（千级线性打分）──▶ top 50 ─┐
      └─embed──▶ 余弦（int8 点积）───────▶ top 50 ─┴─▶ RRF(k=60) ─▶ top 8 ─▶ 生成
```

- 两路各取 50，融合后取 8 块进上下文（约 2500 字，够 1.7B 模型消化）。
- 同一条通知最多贡献 2 块，防止单条长文占满上下文（MMR 的简化替代）。
- 精确重复（同一 `noticeId` + 文本相似度 > 0.95）去重。

### 4.2 结构化预过滤

检索前先按元数据缩小候选集，而不是让向量去理解"上周"：

| 查询里出现 | 过滤条件 |
| --- | --- |
| 今天 / 本周 / 上周 / 本月 / 最近 N 天 | `publishedAt ∈ [from, to]` |
| 教务 / 学工 / 后勤 / 讲座 | `sourceId ∈ 对应集合` 或 `category = ...` |
| 未读 / 重要 | `read = false` / `score ≥ 50` |

过滤在召回之前执行（先缩小候选，再做 BM25 与余弦），既快又准。

### 4.3 拒答阈值

满足任一即判"没有相关内容"，不调生成模型：

- 融合后 top1 的余弦 < 0.35；
- BM25 与稠密两路 top10 无交集（说明两路都不确定）；
- 过滤后候选数为 0。

拒答文案固定："在已抓取的 N 条通知里没有找到相关内容。可以换个说法，或关闭时间筛选再试。"
**明确说"没有"，比编一个像样的答案重要。**

## 5. 查询路由（三档）

这是整个设计里最容易被忽略、但错得最明显的一环。

| 档 | 判定 | 处理 | 例子 |
| --- | --- | --- | --- |
| **结构化** | 含计数/状态/时间聚合词：几个、多少、未读、已完成、今天、本周、逾期 | 直接 SQL 聚合，**不调模型** | 「我有几个未读」「本周有什么到期」 |
| **语义** | 其余问句 | RAG | 「奖学金评选要交什么材料」 |
| **混合** | 既有时间/类别限定，又有语义诉求 | 先过滤，再 RAG | 「这周教务处发的通知里有没有要报名的」 |

规则实现（正则 + 时间词表 + 计数词表），置信度不足时才让模型做一次二分类（可选，端侧小模型足够）。
结构化档的答案由代码生成，因此**数字永远不会错**——这是 RAG 无法保证的。

## 6. 生成

### 6.1 提示词骨架

```
你是校园通知助手。只能依据下面的【片段】回答，不得使用外部知识。
每个结论后面必须标注来源编号，例如 [2]。
如果片段不足以回答，只输出 {"answer":"","insufficient":true}。

【片段】
[1] (2026-11-14 · 教务处 · 校发通知) 关于四六级报名的通知……
[2] (2026-11-12 · 学工部 · 公示公告) 奖学金评选……

【问题】{user_question}
【输出】严格 JSON：{"answer":"...","citations":[{"n":1,"noticeId":"n-xxx","quote":"原文片段"}],
"confidence":0.0,"followups":["..."]}
```

### 6.2 输出校验（防编造）

| 校验 | 规则 | 失败处理 |
| --- | --- | --- |
| JSON 可解析 | 截取首个 `{` 到末个 `}` | 重试 1 次，仍失败则返回纯文本答案且不标引用 |
| 引用编号存在 | `citations[].n` ∈ 片段编号 | 删除越界引用 |
| 引文可核验 | `quote` 必须是对应块 `text` 的子串（去空白后比较） | 该条引用作废；超过半数作废则整答降级为"仅检索结果" |
| 置信度 | 0–1 | 低于 0.4 时 UI 显示"仅供参考" |

"引文必须是原文子串"这条是端侧小模型的关键防线：模型可以编，但编不出恰好存在于块里的字符串。

### 6.3 多轮

保留最近 3 轮；指代消解用规则（"那它呢"→ 拼接上一轮主语）优先，规则失败才让模型改写一次查询。
不做完整的对话记忆——本产品的核心是"查通知"，不是聊天。

## 7. 端侧运行时选型

| 方案 | 优点 | 代价 | 结论 |
| --- | --- | --- | --- |
| **llama.cpp**（GGUF） | Android NEON 成熟；量化生态最全；一个 runtime 可跑嵌入 + 生成 | 需要 CMake + NDK C++ 工具链；静态链接 +3–6 MB/ABI | **首选** |
| candle（纯 Rust） | 免 C++ 工具链，交叉编译最顺；可只做嵌入 | LLM 推理比 llama.cpp 慢；GGUF 支持不如前者完整 | 备选（尤其嵌入层） |
| ONNX Runtime GenAI | Windows 上可走 DirectML | Android 侧体积大、算子覆盖依赖模型 | 不推荐 |
| 纯云端 | 质量最好、零体积 | 违背"全端侧"与隐私前提 | 仅作可选项 |

**模型推荐**

| 用途 | 模型 | 量化 | 体积 | 预期速度（需实测） |
| --- | --- | --- | --- | --- |
| 生成（手机） | Qwen3-1.7B-Instruct | Q4_K_M | ≈ 1.1 GB | SD 7 系 8–15 tok/s |
| 生成（桌面） | Qwen3-4B-Instruct | Q4_K_M | ≈ 2.5 GB | 20–35 tok/s |
| 嵌入 | bge-small-zh-v1.5 | int8 / GGUF | ≈ 24–30 MB | 单块 < 10 ms（桌面） |

> 速度是**预期区间**，不是实测值。R4 阶段必须在目标机型上跑一遍再写死默认档位。

### 7.1 内存与降级

| 设备内存 | 策略 |
| --- | --- |
| ≥ 8 GB | 4B 生成 + 嵌入常驻 |
| 4–8 GB | 1.7B 生成；空闲 5 min 卸载模型 |
| < 4 GB | 仅检索 + 抽取式回答（把 top 块的原文按 RRF 顺序拼给用户），不加载生成模型 |

"抽取式回答"是兜底形态：不生成、只排序与摘录。它在任何设备上都能工作，
也是端侧方案能在低端机上活下来的原因。

## 8. 模型分发与校验

1. 安装包**不含**模型；首次进入"智能问答"时提示下载（约 1.1 GB）。
2. 来源：项目 Release 资产或用户自选本地文件（`import_model`）。
3. 校验：`SHA-256` + 文件大小；不匹配拒绝加载并删除半包。
4. 断点续传：HTTP Range；失败可重试，不阻塞其他功能。
5. 目录：`{app_data}/models/{model-id}/`，与 `index/` 分离，卸载模型不影响索引（索引会标记失效待重建）。
6. 许可：Qwen 系列 Apache-2.0、bge MIT，随包附 `MODEL-LICENSE.txt`。

## 10. 评估

### 10.1 数据集

60 题，全部来自真实通知：

| 类型 | 数量 | 判定 |
| --- | --- | --- |
| 可答（答案在语料内） | 30 | 引用命中 + 答案包含关键实体 |
| 不可答（语料里确实没有） | 15 | 必须拒答，不得给"看起来合理"的答案 |
| 结构化（计数/时间/状态） | 15 | 数字与 SQL 结果完全一致 |

### 10.2 指标

| 指标 | 阈值 | 测法 |
| --- | --- | --- |
| Recall@5 | ≥ 0.85 | 标注的正确块是否进前 5 |
| MRR | ≥ 0.65 | 正确块排名倒数均值 |
| 引用支撑率 | ≥ 0.95 | 答案中的 [n] 有对应原文子串 |
| 拒答准确率 | ≥ 0.90 | 15 道不可答题中正确拒答的比例 |
| 结构化正确率 | 100% | 与 SQL 逐条比对 |
| 检索延迟 p95 | ≤ 200 ms | 1000 块，桌面与手机各测 |
| 端到端 p95 | ≤ 3 s（手机）/ ≤ 1.5 s（桌面） | 含生成 |

## 11. 分阶段步骤

| 阶段 | 内容 | 出门门槛 |
| --- | --- | --- |
| **R0 索引** | 切块 + 嵌入 + `index/` 落地 + 增量 | 400 条通知索引 ≤ 60 s（桌面）；重建后 `count` 一致 |
| **R1 检索** | BM25 + 余弦 + RRF + 元数据过滤（**已实现内核**） | 用固定向量跑 60 题，Recall@5 ≥ 0.85 |
| **R2 路由** | 三档判定 + SQL 直答 | 15 道结构化题 100% |
| **R3 生成** | 端侧 llama.cpp 接入 + 引用校验 | 引用支撑率 ≥ 0.95，不可答题拒答 ≥ 0.9 |
| **R4 评估** | 目标机型实测速度与内存 | 中端 Android 首 token ≤ 3 s，峰值内存 ≤ 1.5 GB |
| **R5 分发** | 模型下载 / 校验 / 导入 / 降级 | 断网、半包、校验失败三种情况都不崩 |

R1 可以完全离线做——`cn-rag` 的接口不依赖模型，用哈希向量或固定向量就能验证排序逻辑。

## 12. 风险

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 1.7B 模型中文公文理解弱 | 答案空泛、漏要点 | 引用校验 + 抽取式兜底；桌面默认 4B |
| 端侧幻觉 | 编造截止时间 | 时间类一律以 `find_deadline` 的规则结果为准，模型无权覆盖 |
| 手机内存不足 | 崩溃/被杀 | 分档降级；模型空闲卸载；`< 4 GB` 只做检索 |
| 嵌入模型对校务术语不敏感 | 召回偏低 | 用真实通知做 Recall 评估；必要时换 base 版（768 维，体积 +3 倍） |
| 索引与数据不一致 | 答非所问 | 派生 + 版本号 + 启动校验 + 自动重建 |
| 模型许可 | 分发合规 | 只分发 Apache-2.0 / MIT 模型，附许可文件 |

## 13. 已落地与未落地

**已落地（本仓库）**

- `crates/cn-rag`：`chunk_notice` / `tokenize` / `Bm25` / `cosine` / `normalize` / `quantize_i8` / `rrf_fuse`，
  11 个单测全绿（GNU 工具链 `cargo test`），`cargo clippy --lib` 无告警。

**未落地（依赖外部资源）**

- 嵌入模型与生成模型（体积以 GB 计，需下载）；
- llama.cpp 的 Android 交叉编译（需 NDK + CMake）；
- 60 题评估集（需真实通知语料与人工标注）。

这三项都无法在没有模型与语料的情况下凭空完成，所以本文把它们放在 R0/R3/R4，而不是假装已经实现。
